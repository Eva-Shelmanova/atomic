# Реестр проектных решений

Формат: контекст → решение → рассмотренные альтернативы → последствия. Номер решения указывается в коде и конфигурации там, где оно применяется.

---

## D-001. Базовая версия и ветка разработки

**Контекст.** Требование 1 задания: сохранить работоспособность базового ассистента. Нужна точка отсчёта для регрессии.
**Решение.** Коммит a3f0e16 (ассистент 6-го семестра) помечен тегом `v0.1-baseline`. Разработка идёт в ветке `diploma`, каждый законченный шаг — отдельный коммит, каждый этап — тег.
**Последствия.** Любое изменение поведения базового ассистента обнаруживается сравнением с тегом; быстрые тесты базовой версии прошли 24.10.2026 (`test-results/2026-10-24-baseline.txt`).

## D-002. Бинарные материалы и данные вне git

**Контекст.** В корне лежали .pages/.pdf/.docx отчётов, а сырые данные NPPAD занимают сотни мегабайт.
**Решение.** В git только код, конфигурация, тексты и документация. Бинарные документы (`*.pages`, `*.pdf`, `*.docx`, …), `NPPAD/raw/`, `data/processed/`, `data/models/`, `ETHDB/` в `.gitignore`. Данные восстанавливаются скриптами из `scripts/`.
**Альтернативы.** Git LFS — избыточно для одного автора и требует квоты GitHub.

## D-003. Источник NPPAD: CSV из репозитория авторов

**Контекст.** Репозиторий thu-inet содержит исходные базы PCTRAN (.mdb, ~15 ГБ) и их CSV-копии (`Operation_csv_data`, 605 МБ). Свободное место на диске после клонирования упало до 16 ГБ.
**Решение.** Используется `Operation_csv_data` (коммит a8d54ed, 25.08.2026). Файлы .mdb удалены из локальной копии сразу после проверки, что CSV покрывают все прогоны (для класса RI существуют только CSV). Файлы `Transient Report.txt` сохранены: из них берутся тяжесть и номер неисправности.
**Последствия.** `Variable_Power_Data` (12 сценариев изменения мощности) доступен только в .mdb; для чтения нужен mdbtools. Отложен до этапа C как внешний стресс-тест. `Dose_csv_data` (радионуклиды) пока не используется.

## D-004. Состав классов: 12 для обучения и benchmark, 6 как пробы

**Контекст.** Шесть классов NPPAD (ATWS, LACP, LOF, Normal, SP, TT) представлены единственным прогоном. Дорожная карта требует разбиения по прогонам, а не по окнам.
**Решение.** Генератор обучается и оценивается на 12 классах, где ≥ 99 прогонов разной тяжести. Шесть однопрогонных классов — «пробы вне распределения»: на них проверяется, что верификатор не подтверждает гипотезы из чужого множества классов.
**Альтернативы.** Делить единственный прогон по времени — соседние окна одного прогона окажутся и в обучении, и в тесте, оценка будет завышена.
**Последствия.** Класс «нормальная эксплуатация» не входит в обучаемое множество; это ограничение фиксируется в отчёте.

## D-005. Лишние столбцы в 25 файлах SLBIC

**Контекст.** В 25 из 101 файлов SLBIC есть столбцы WPCS, WPMU, WPFW, которых нет в таблице параметров README.
**Решение.** Столбцы отбрасываются; список задан в `config/channels.toml` (`ignored_columns`). Любой другой неожиданный столбец — ошибка загрузки.

## D-006. Шесть разрешённых каналов генератора

**Контекст.** Дорожная карта: генератор видит ограниченный набор каналов (6 из 97), набор задаётся в конфигурации.
**Решение.** По одному каналу на каждую из шести критических функций безопасности PWR (Critical Safety Functions), которые оператор контролирует в первую очередь:

| Функция безопасности | Канал | Величина |
|---|---|---|
| подкритичность | PWNT | мощность по нейтронному потоку, % |
| охлаждение активной зоны | TAVG | средняя температура теплоносителя, °C |
| теплоотвод | PSGA | давление в ПГ A, bar |
| целостность первого контура | P | давление в первом контуре, bar |
| защитная оболочка | PRB | давление в здании реактора, bar |
| запас теплоносителя | LVPZ | уровень в компенсаторе давления, % |

**Обоснование.** Набор отражает то, что оператор видит «с первого взгляда», и не подбирается под точность классификатора. Он намеренно неполон: например, разрывы трубок ПГ A и ПГ B по этим каналам различаются плохо. Различение должен обеспечить верификатор, который видит все каналы (NSGA/NSGB, RM2 и др.). В этом и состоит смысл архитектуры «гипотеза по части данных → независимая проверка по всем».
**Последствия.** Канал ПГ представлен только петлёй A — асимметрия зафиксирована и обсуждается в отчёте.

## D-007. Каналы label_proxy

**Контекст.** Часть параметров PCTRAN описывает саму неисправность: расход и энергию течи, течь трубок ПГ, разрыв питательной линии. Штатными приборами они не измеряются и фактически кодируют метку.
**Решение.** Восемь каналов помечены `label_proxy = true`: WLR, HLW, WBK, MBK, EBK, WTRA, WTRB, WFLB. В генератор они не допускаются (проверка конфигурации и контрактный тест). В верификатор по умолчанию тоже (`verifier.exclude_label_proxy = true`), иначе проверка гипотез станет тривиальной, а benchmark — нечестным.
**Альтернативы.** Отдать верификатору буквально все 96 каналов — формально ближе к тексту требования 6, но результат проверки потерял бы смысл.

## D-008. Окна наблюдений

**Решение.** Окно — 12 точек (120 с при шаге 10 с), сдвиг — 6 точек (60 с). Параметры в `config/diagnostics.toml`. Время от начала прогона хранится в окне только для оценщика и трасс; генератору не передаётся.
**Последствия.** 18 прогонов RI короче 120 с не дают ни одного окна; это учитывается в статистике.

## D-009. Граф знаний в памяти

**Контекст.** Требование 3: единая семантическая модель диагностической информации.
**Решение.** Граф знаний реализован в памяти (`atomic/knowledge/schema.py`) с явной схемой допустимых связей и сериализацией в JSON. Отдельная графовая СУБД (Neo4j и т.п.) не используется.
**Обоснование.** Объём — тысячи узлов на сценарий; важнее проверяемая схема и воспроизводимость, чем масштабирование. Добавление СУБД усложнило бы развёртывание без выигрыша для диплома.

## D-010. Конфигурация в TOML, Python ≥ 3.11

**Решение.** Конфигурация диагностики, реестр каналов и пакеты правил — TOML-файлы в `config/`, читаются стандартным `tomllib`. Минимальная версия Python поднята до 3.11 (рабочее окружение — 3.12.12).
**Альтернативы.** YAML — нужна внешняя зависимость; JSON — без комментариев, а обоснования параметров должны быть рядом с параметрами.

## D-011. Разбиение и нормализация

**Решение.** Разбиение train/val/test = 60/20/20 по прогонам, стратифицированное по сценарию, seed 42. Нормализация z-score; среднее и σ считаются только по train-прогонам. Каналы, постоянные на train (7 шт.), получают σ = 1.

## D-012. Непрозрачные идентификаторы

**Контекст.** Пути NPPAD содержат имя сценария (`LOCA/12.csv`). Если такой путь попадёт в id, генератор «узнает» ответ из идентификатора.
**Решение.** `run_id` = первые 12 символов SHA-256 от `nppad:<сценарий>/<файл>`, `window_id` = 16 символов SHA-256 от `<run_id>:<начало>`. Исходный путь хранится только в `labels.json`.

## D-013. Тяжесть аварии

**Решение.** Тяжесть берётся из первой строки `Malfunction # N Fraction = X %` в Transient Report, номер неисправности — оттуда же. Для RI доля отрицательная (имена файлов −1…−100). Проверено: у всех многопрогонных классов тяжесть совпадает с номером файла, как указано в README.

## D-014. Режимы верификатора ответа: off / shadow / enforce

**Контекст.** Требование 1 (не сломать базовый ассистент) и требование 9 (детерминированная проверка ответа) конфликтуют: если в обычном чате сразу применять решения, ответы аналитика станут помеченными, а поведение 6-го семестра изменится. Документ «Upgrade» рекомендует вводить новые слои сначала в теневом режиме.
**Решение.** Переменная `ATOMIC_VERIFICATION_MODE`: `off` — проверки нет; `shadow` (по умолчанию) — решение вычисляется и пишется в трассу Langfuse, текст не меняется; `enforce` — BLOCK заменяет ответ заглушкой, REQUIRE_HUMAN добавляет пометку с причинами. В режиме enforce в память чата пишется только выпущенный текст. Диагностический контур (этап C) работает только в enforce.
**Последствия.** Регрессионные тесты базового ассистента проходят без изменений; метод `ask() -> str` сохранён, добавлен `ask_verified()`.

## D-015. Доверие к источнику назначает политика, а не агент

**Контекст.** В проекте 7-го семестра `trust_base` — «базовый вес класса источника, задаётся политикой домена». Если агент сам присылает trust_base, он может завысить уверенность ответа.
**Решение.** Агент указывает только вид источника и id. Верификатор подставляет `trust_base` из пакета правил: нормативный документ 0,95, телеметрия 0,9, вывод инструмента 0,8, фрагмент базы знаний 0,7, историческое событие 0,6, текст модели 0,2, подтверждение человека 1,0. Порог выпуска без пометки `min_confidence = 0,5`.
**Последствия.** Значения доверия версионируются вместе с правилами (`aes-core-1.0.0`); их изменение — новая версия пакета.

## D-016. Гранулярность утверждений — весь ответ агента

**Решение.** На этапе B каждый агент формирует одно утверждение на ответ: Retriever — «ответ основан на фрагментах X, Y», Command — «результат запуска exec:…», Analyst — рассуждение модели. Разбиение ответа на отдельные утверждения с привязкой каждого к источнику — задача этапа C, где AnalystAgent будет объяснять пакет гипотез.
**Ограничение.** Правило REF_RESOLVABLE проверяет, что фрагменты существуют, но не то, что LLM действительно опирался на них. Это фиксируется в отчёте как ограничение текущей версии.

## D-017. Пустой результат поиска — REQUIRE_HUMAN, а не BLOCK

**Решение.** Если Retriever не нашёл фрагментов, его утверждение опирается только на текст модели (MODEL_GENERATED). Правило NO_MODEL_ONLY (warning) переводит ответ в REQUIRE_HUMAN. Блокировка оставлена для ответов без утверждений и для неразрешимых ссылок.
**Обоснование.** Честное «в базе знаний нет информации» полезно оператору; блокировать его — значит скрывать отсутствие данных.

## D-018. Тесты не отправляют трассы в Langfuse

**Контекст.** Ключи Langfuse подтягиваются из `.env`; при остановленном Langfuse каждый тест ждал таймаута экспорта (60 тестов — 22 с вместо 0,7 с).
**Решение.** `tests/conftest.py` обнуляет ключи Langfuse, если не задано `ATOMIC_TEST_LANGFUSE=1`.

## D-019. Генератор гипотез — классический классификатор без LLM

**Контекст.** Документ «Upgrade» (этап 2) описывает интерпретацию на основе классификационных моделей и правил; дорожная карта требует калибровки уверенности (опасность H4).
**Решение.** Признаки окна по 6 каналам (уровень в начале и конце, среднее, σ, минимум, максимум, наклон; 42 признака). Два кандидата scikit-learn: логистическая регрессия и градиентный бустинг на гистограммах (HistGradientBoosting). Выбор — по log-loss на val после калибровки. Калибровка — температурное масштабирование вероятностей на val (один параметр T, минимизация NLL).
**Результат на val.** Выбран бустинг: top-1 0,786, top-3 0,998, ECE 0,055 → 0,029 после калибровки (T = 1,67). Логистическая регрессия: top-1 0,652, top-3 0,977.
**Альтернативы.** LLM-классификатор — недетерминирован, плохо калибруется и противоречит идее «LLM только структурирует». Нейросеть на сырых рядах — избыточна для 42 признаков и хуже объяснима.

## D-020. Фильтр базы событий ETHZ

**Решение.** Из 1561 события листа «ReMerged DB_public» оставлены события на энергетических АЭС (Industry = Energy, Facility = Plant), не помеченные авторами как исключённые (OMIT ≠ 1), с реактором PWR (как в NPPAD). Осталось 783 события. Исключено: другой тип реактора — 473, OMIT — 191, не АЭС — 97, не энергетика — 17.

## D-021. Подбор аналогов: BM25 + таблица соответствия

**Решение.** Для каждого сценария NPPAD в `config/analogues.toml` задан английский запрос и список систем-источников ETHZ (значения сверены с базой). Оценка — BM25 по описанию, системе-источнику и причине события (слова и биграммы), ×1,5 при совпадении системы-источника, порог 3,0. Дубли (одно событие на нескольких энергоблоках) отбрасываются по станции, дате и началу описания.
**Ограничение.** Качество аналогов оценено качественно (просмотр выдачи по всем классам). Разметка релевантности для precision@k — задача этапа C.

## D-022. Параметры верификатора гипотез подобраны на val с приоритетом безопасности

**Контекст.** При исходных параметрах (min_weight 0,3; top 15; порог подтверждения 0,7) верификатор подтверждал 30 % неверных гипотез.
**Решение.** Перебор 24 сочетаний на val (`scripts/sweep_verifier.py`). Критерий: максимум доли подтверждённых верных гипотез при доле подтверждённых неверных ≤ 10 %; варианты, уступающие лидеру менее чем на 0,005, считаются равными, и среди них берётся больший top-1 после проверки. Выбрано: min_weight 0,7; top_channels 15; confirm_threshold 0,6.
**Обоснование.** Для АЭС ложное подтверждение опаснее, чем «не определено»: неопределённость оставляет решение оператору, ложное подтверждение усиливает automation bias.
**Цена.** Доля подтверждённых верных гипотез снижается с 0,93 до 0,73; остальные чаще получают статус «не определено», а не «отклонено».

## D-023. Контрастная проверка гипотез

**Решение.** Вес признака при проверке гипотезы s — средняя по конкурентам из того же top-k доля окон конкурента, выходящих за типичный диапазон s (матрица специфичности по train). Верификатор проверяет то, что отличает s именно от альтернатив, а не от всех классов сразу. Если гипотеза одна, конкурентами считаются все прочие сценарии.
**Последствие.** Когда различающих признаков нет (течь в горячей и холодной нитке на уровне окна), обе гипотезы получают «не определено» с явной причиной.

## D-024. Хэш конфигурации данных — только по разделам, влияющим на данные

**Решение.** В манифест данных и метаданные моделей пишется хэш разделов seed, windows, split, scenarios, generator. Изменение порогов верификатора не делает данные и генератор «устаревшими».

## D-025. Выборка test не используется до benchmark этапа C

**Решение.** На этапе B метрики считаются только на val (выбор модели, калибровка, подбор порогов) и на пробах вне распределения. Скрипт оценки отказывается работать на test. Итоговые числа для отчёта получаются на test на этапах C и E.

## D-026. BM25 в in-memory памяти вместо поиска по подстроке

**Контекст.** Отчёт 6-го семестра заявлял «BM25 как запасной путь» поиска, но in-memory память искала по подстроке и пересечению слов.
**Решение.** `atomic/memory/bm25.py` (без внешних зависимостей) используется и для аналогов ETHZ, и для поиска в `VectorMemory`, когда PostgreSQL недоступен. Регрессионный тест retrieval остаётся зелёным.

## D-027. ETHZ_Database_Access_tool.xlsm — интерфейс к Support_file.xlsx

**Контекст.** Инструмент ETH Zurich распространяется как книга Excel с макросами; все его листы (Events, Failure Sequences и др.) в файле пусты.
**Анализ.** Код VBA (извлечён `olevba`): при открытии показывается форма фильтров (регион, тип реактора, значимость, тип события, исходное событие и т. д.), затем макрос открывает `Support_file.xlsx` из той же папки, копирует подходящие строки листа «ReMerged DB_public (MOST CURRENT)» в лист Events, строит лист Failure Sequences (цепочка отказов по уровням 0/11/21/31) и статистику. Ссылки на первоисточники ведут на `xyotta.com/.../<номер>.pdf`.
**Решение.** Логика выборки воспроизведена в `scripts/load_ethz.py` на Python (тот же лист, те же поля), без Excel и макросов. Дополнительно забираются поля, которые использует инструмент: тип исходного события (Initiating Event), система, компонент, краткое описание, частичный отказ, цепочка отказов.

## D-028. Аналоги: структурное совпадение по типу исходного события

**Решение.** Для каждого сценария NPPAD в `config/analogues.toml` задан список типов исходного события ETHZ (например, SGATR/SGBTR → Steam Generator Tube Rupture; LOCA/LOCAC/LLB → SBLOCA/MBLOCA/LBLOCA; RW/RI → RIA). События с совпавшим типом ранжируются первыми (`match_basis = initiating_event`), затем добираются текстовыми совпадениями BM25.
**Результат.** Точность@3 на размеченных событиях: текстовый поиск 0,643 → совмещённый 0,936 (`test-results/2026-10-24-analogues-eval.json`). Остаточные промахи — для разрыва паропровода в базе всего одно размеченное событие.

## D-029. Variable_Power_Data — внешний стресс-тест

**Решение.** Базы .mdb читаются чистым Python (пакет `access-parser`, dev-зависимость), `scripts/convert_variable_power.py` пишет CSV в формате Operation_csv_data. Временной порядок восстанавливается сортировкой; в части файлов после точки 0 с есть разрыв до 726–1370 с — окна не пересекают разрыв. 12 прогонов в обучение не входят: 4 нормальных изменения мощности проверяют ложные идентификации, 8 аварий на переходном режиме — устойчивость к другой рабочей точке.

## D-030. Память о событии (EpisodeContext) и сигнатуры ранней фазы

**Контекст.** По одному окну течь в горячей и холодной нитке не различалась (точность бинарного классификатора по 574 признакам окна — 0,54). Эксперимент показал, что в первые 300 с процессы различаются (бустинг на ранних окнах — 0,885), а по изменениям каналов через 30/60/120 с от начала события относительно исходного состояния 40 val-прогонов разделяются без ошибок; результат устойчив к измерительному шуму до 5 % от значения и к исключению 8 самых информативных каналов.
**Решение.** Верификатор получает память о событии: исходное состояние и наблюдения первых 120 с — только уже прошедшие на момент текущего окна (причинность). Сигнатуры ранней фазы (246 признаков: 82 канала × Δ30/Δ60/Δ120) строятся по одному вектору на train-прогон тем же квантильным методом, что оконные. В NPPAD начало события — начало прогона (точка 0 с — стационар до ввода неисправности в 0,5 с); в эксплуатации — момент первой сигнализации.
**Что не менялось.** Генератор по-прежнему видит только текущее окно 6 разрешённых каналов (барьер, D-006).

## D-031. Параметры верификатора с памятью и без неё

**Решение.** С памятью о событии: min_weight 0,5, порог подтверждения 0,7, по 15 признаков окна и ранней фазы. Без памяти (ассистент подключился посреди события): строгие параметры прежнего этапа — min_weight 0,7, порог 0,6. Подбор — тем же критерием D-022 на val (`test-results/2026-10-25-verifier-sweep-val.json`).

## D-032. Проверка отклонения и новизны

**Решение.**
1. Проверка отклонения: канал отклонился, если |x − x0| / max(|x0|, 10⁻³) > 1 %; четыре канала, дрейфующие и без события (HTR, RBLK, RHFL, RHMT — установлено по прогонам ATWS/SP/MD), не считаются; событие есть, если отклонился хотя бы один канал. Иначе исход «отклонений не обнаружено».
2. Новизна: расстояние до ближайшего train-события по признакам ранней фазы (робастная нормировка, только наблюдённые признаки) и до ближайшего train-окна; порог — 99-й перцентиль на val (суммарно 2 % ложных тревог на известных сценариях). Превышен любой порог — исход «не похоже ни на один известный сценарий».
**Ограничение.** Новый сценарий, похожий на известный (например, разрыв трубки ПГ A при известном ПГ B), принципиально неотличим от известного: при исключении одного класса из эталона он распознаётся как новый в среднем лишь в 43 % окон (пересчёт на 11 классах, `test-results/2026-10-25-novelty-loco-val.json`; по ранней фазе — 33 %, по окну — 28 %). Хорошо отделяются LLB, LR, RI, SLBIC (89–100 %), почти не отделяются LOCA/LOCAC (друг через друга), SLBOC, RW, SGATR (0–12 %).

## D-033. Итоговое правило выбора

**Решение.** нет отклонения → NO_ANOMALY; новое событие → NOVEL; нет подтверждённых гипотез → UNCONFIRMED; одна подтверждённая или лидер опережает вторую подтверждённую по доле подтверждений не меньше чем на 0,1 → IDENTIFIED; иначе AMBIGUOUS.
**Подбор на val.** Допуск 0 / 0,05 / 0,1 / 0,2 / 0,3: точность IDENTIFIED 0,978 / 0,995 / 0,996 / 0,996 / 0,996 при покрытии 0,923 / 0,886 / 0,882 / 0,847 / 0,823. Выбран 0,1.

## D-034. Аудит данных: «пустые» классы NPPAD

**Найдено.** Сравнение каждого прогона с прогоном без события (ATWS: неисправность с долей 0 %):
- MD (100 прогонов) совпадает с ним полностью при любой заявленной тяжести (1…100 %): концентрация бора постоянна (200 ppm);
- SLBOC (100 прогонов) отличается не более чем на 0,001σ — теплогидравлически стационар, меняются только мониторы радиации паропровода и конденсатора (RM2, RM3, DTHY);
- ATWS и SP — неисправность с долей 0 %, станция в стационаре;
- Normal — не стационар: в начале закрывается клапан питательной воды, открываются предохранительные клапаны.
**Решение.** MD исключён из обучаемых классов (11 классов вместо 12): его прогоны вместе с ATWS и SP — эталон «без события», на них система должна отвечать «отклонений не обнаружено». SLBOC сохранён со слабой (только радиационной) сигнатурой; это ограничение. LACP, LOF, Normal, TT — пробы вне обучаемого множества (ожидается «новое»).
**Последствие.** Прежние результаты для MD (78 % top-1 на этапе B) — артефакт: модель распознавала «ничего не происходит». Метрики этапа B для 12 классов сохранены в журнале как исторические; итоговые числа — по 11 классам.

## D-036. Диагностический ответ: детерминированный отчёт + пояснение со ссылками

**Решение.** AnalystAgent (`explain_diagnosis`) строит ответ из DiagnosticReport детерминированно: оценка ситуации, гипотезы со статусами, свидетельства [E…] со ссылками `<окно>#<канал>`, аналоги [A…] со ссылками `ethz:<номер>`. Пояснение LLM необязательно; оно разбирается по предложениям: предложение со ссылками опирается на них, без ссылок — только на текст модели (→ NO_MODEL_ONLY → REQUIRE_HUMAN), несуществующая ссылка → REF_RESOLVABLE → BLOCK. `AtomicWorkflow.diagnose()` всегда работает в режиме ENFORCE; ссылки на окна разрешает источник телеметрии (`TelemetryReplay`, только чтение), на события — база ETHZ. В трассу Langfuse пишутся этапы (гипотезы, проверка, новизна) и VerificationBundle.

## D-038. Попарный отбор признаков при проверке с памятью о событии

**Контекст.** Первый итоговый прогон на test (`test-results/2026-10-25-benchmark-test-v1-mean.json`) показал, что течь в горячей нитке (LOCA) в 50 % окон получает исход AMBIGUOUS. Разбор на val: это малые течи (тяжесть до 20 %); 15 признаков, отобранных по средней специфичности против всех конкурентов, отличали LOCA от разрыва трубки ПГ, но не от LOCAC — обе течи подтверждались на 100 %.
**Решение.** С памятью о событии для каждого конкурента берутся свои top_n/|O| признаков с наибольшей специфичностью именно против него (`contrast = "pairwise"`). Без памяти сохранён прежний средний отбор: на val попарный отбор без памяти подтверждал 25 % неверных гипотез.
**Подбор на val** (критерий D-022): попарный, 15 признаков, порог 0,7 — подтверждено верных 0,968, неверных 0,016; покрытие IDENTIFIED 0,946 при точности 0,995; LOCA установлена в 97 % окон, неоднозначных исходов 0,6 % (было: 0,940 / 0,053; 0,882 / 0,996; 52 %; 4,2 %).
**Методологическая оговорка.** Проблема замечена на test, исправление разработано и настроено только на val. Итоговый прогон test (`2026-10-25-benchmark-test.json`) поэтому не полностью «нетронутый»; в отчёте приводятся оба прогона. Для финальных чисел ВКР на этапе E test-выборка обновляться не будет, а система будет заморожена до прогона.

## D-039. Причинное определение начала события на внешнем стресс-тесте

**Контекст.** В итоговом прогоне с попарным отбором (D-038) нормальное снижение мощности 100→80 % (Variable_Power, NORM_100_to_80) в 18 % окон получило исход IDENTIFIED (LR — сброс нагрузки), в прогоне v1 — 0 %. Разбор: для нормальных прогонов память о событии отсчитывалась от начала записи, а снижение мощности начинается около 420 с, поэтому признаки ранней фазы описывали стационар, и проверка новизны по эпизоду не срабатывала (расстояние 0,001 при пороге 1,31). Оконная проверка видела плавное снижение нагрузки, физически похожее на LR. Для аварийных прогонов начало бралось из манифеста (момент ввода неисправности) — это оракульная информация, недоступная в эксплуатации.
**Решение.** Начало события определяется причинно: последняя стационарная точка не позже текущего момента; точка стационарна, если ни один наблюдаемый недрейфующий канал не изменился больше порога проверки отклонения (1 %) за предыдущие 60 с (`stationary_points`, `detect_onset` в `atomic/diagnostics/variable_power.py`). Пусковой переходный процесс (RH, WECS, WCHG в первые ~100 с прогонов 100→80) этим правилом не принимается за начало события. Оракульный режим оставлен в benchmark только для сравнения (`variable_power_oracle_onset`).
**Согласованность.** На всех 222 test-прогонах NPPAD детектор даёт первое отклонение на первом шаге (≤ 10 с), то есть совпадает с принятым началом t = 0 (`ds.episode`); обучающая выборка и сигнатуры не меняются.
**Результат.** Variable_Power: ложных идентификаций до ввода неисправности 0 (было 18 % на NORM_100_to_80), неверных после ввода 0 (было 3,4 % на SGATR_80_to_100); нормальные изменения мощности и аварии на фоне изменения мощности получают исход NOVEL — режим вне обучающей выборки.
**Ограничение.** Новое стационарное состояние сбрасывает событие: после выхода станции на новый уровень проверка отклонения сравнивает с ним. Для эксплуатации нужна политика «защёлкивания» события (вне объёма этапа C). Регрессия замечена на внешнем стресс-тесте, а не на test NPPAD; test-выборка исправлением не затронута.


## D-040. Ссылки на документацию в диагностическом ответе

**Контекст.** Дорожная карта (этап C): AnalystAgent пишет объяснение «со ссылками на документацию». Диагностический ответ ссылался только на телеметрию и события ETHZ.
**Решение.** Для установленного сценария (исход IDENTIFIED) `diagnose` ищет фрагменты базы знаний по коду и названию сценария; до двух фрагментов попадают в ответ как справочные материалы [D1], [D2] с утверждениями типа RAG_CHUNK (доверие 0,7), которые разрешаются через `has_id` векторной памяти. Отбор: у pgvector — косинусная близость не ниже 0,6, у BM25 — ненулевая оценка; фрагменты с указаниями к действию (шаблоны правила NO_DIRECTIVES) не используются. Для исходов NOVEL, UNCONFIRMED, AMBIGUOUS справочные материалы не добавляются: они относились бы к неустановленному сценарию. Недоступность базы знаний не мешает диагностическому ответу.
**Ограничение.** Текущая база знаний ассистента (`dataset/`, 4 файла, 2,6 КБ) описывает только работу ИТ-системы; документов по аварийным сценариям в ней нет, поэтому в прогонах этапа C раздел [D…] пуст. Механизм покрыт тестом; наполнение базы знаний документами по сценариям (с указанием источника) — задача этапа E.

## D-041. Откат к детерминированному ответу при блокировке пояснения LLM

**Контекст.** Оценка на Ollama (qwen2.5-7B) показала, что модель иногда ссылается на несуществующие свидетельства (в пробах TT и MD) или пишет предложения без ссылок. Верификатор ответа блокировал ответ целиком, хотя детерминированная часть, построенная из `DiagnosticReport`, корректна.
**Решение.** Если ответ с пояснением получает BLOCK, `diagnose` отбрасывает пояснение и заново проверяет детерминированный ответ. В ответ добавляется пометка «Пояснение языковой модели не выпущено…» с нарушенными правилами. Отклонённый `VerificationBundle` и текст пояснения сохраняются в метаданных ответа и трассы Langfuse (`narrative_rejected`) для аудита. REQUIRE_HUMAN пояснение не отбрасывает: оно выпускается с пометкой, как и прежде.
**Альтернатива.** Блокировать весь ответ — безопасно, но оператор теряет проверенную диагностику из-за ошибки необязательного компонента. Повторный запрос к LLM — недетерминирован и увеличивает задержку.
**Безопасность.** Заблокированный текст LLM не попадает ни в ответ, ни в память чата; детерминированная часть проходит те же правила.
